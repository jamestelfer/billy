# Tailscale setup

What the tailnet needs before `billy` can serve anything. All of it is admin
console configuration — none of it is code, and none of it can be worked
around from the binary.

`billy` embeds a Tailscale node (`tsnet`) and calls `ListenFunnel("tcp", ":443")`.
Before that returns a listener, tsnet checks three things via
`ipn.CheckFunnelAccess`. Miss any one and startup fails with the message
quoted below rather than with anything about Alexa.

## 1. HTTPS certificates enabled on the tailnet

**DNS** → **HTTPS Certificates** → Enable. MagicDNS must be on first.

Without it: `Funnel not available; HTTPS must be enabled.`

This page is also where you read the tailnet name. The Funnel URL is
`https://<hostname>.<tailnet>.ts.net` — `<hostname>` defaults to `billy` and
is set by `BILLY_HOSTNAME`; `<tailnet>` is your domain or an autogenerated
`tailXXXX.ts.net`.

## 2. The `funnel` node attribute

In the policy file (**Access controls**). Tag-based is the better fit for a
headless service: the node is owned by the tag rather than by a person, so it
survives your account changing.

```jsonc
"tagOwners": {
  "tag:billy": ["autogroup:admin"],
},
"nodeAttrs": [
  { "target": ["tag:billy"], "attr": ["funnel"] },
],
```

Without it: `Funnel not available; "funnel" node attribute not set.`

If you would rather the node be user-owned, drop the `tagOwners` entry and
target `autogroup:member` or your own login instead — but then use an
untagged auth key in step 4.

## 3. Port 443

Already satisfied, and not configurable. Funnel permits only 443, 8443 and
10000; `billy` hardcodes 443 because the Alexa service requires the skill
endpoint there.

## 4. A reusable, non-ephemeral auth key

**Settings** → **Keys** → **Generate auth key**:

| Setting | Value | Why |
|---|---|---|
| Reusable | yes | So re-registering the node does not need a new key |
| Ephemeral | **no** | An ephemeral node deregisters on shutdown and returns with a new identity — the Funnel URL would change, and it is pinned in the Alexa developer console |
| Tags | `tag:billy` | `billy` does not set `AdvertiseTags`, so the tag has to come from the key. Omit if you took the user-owned route in step 2 |
| Pre-approved | if device approval is on | Otherwise the node registers and then sits unapproved, and Funnel never comes up |

Pass it as `TS_AUTHKEY`. It is only needed for the first run — after that the
node identity lives in the state directory (`BILLY_STATE_DIR`).

Auth keys expire after 90 days at most. **Note the expiry date**: the service
keeps running past it on its persisted identity, but re-registering after a
state loss will not work. A tagged OAuth client is the longer-term answer.

## What you do *not* configure

`ListenFunnel` reads the serve config and writes it itself when absent, so
there is nothing to set up under **Machines** → the node → **Serve**. Do not
hand-configure it.

## A note on who can reach the listener

`ListenFunnel` listens on both the tailnet and the internet by default. Funnel
traffic is gated by the `funnel` node attribute above; the tailnet-side path is
governed by your ordinary ACL rules. Passing `tsnet.FunnelOnly()` would
restrict it to internet traffic only. For a capture endpoint the default is
more useful — it lets you exercise `/healthz` and `/alexa` from another tailnet
machine before involving Alexa at all.

## Verifying

From a machine with **no** Tailscale installed, on a different network:

```
curl -v https://<hostname>.<tailnet>.ts.net/healthz
```

Expect `200`, no TLS warnings, and a certificate chaining to a public CA whose
SAN matches the Funnel hostname. First run provisions that certificate and can
take several seconds — `ListenFunnel` blocks for it rather than failing, so a
slow first start is expected, not a fault.

Then stop and restart the process: the URL must be identical and `/healthz`
must recover without re-authing. If the URL changed, the node registered as
ephemeral or the state directory was not persisted.
